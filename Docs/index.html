这本书想解决什么问题#

很多人第一次接触 DeepSeek Harness（命令行里叫 dsh）时，会卡在同一个地方：文档里反复出现 profile、插件、补丁、运行模式、MCP 挂载，每个词单看都认识，连起来就不知道从哪下手。

本书不做术语罗列，而是按“一个人真实会走的路径”来组织：

  1. 先弄清楚它到底解决了什么问题（第 1 章）；
  2. 把它装起来、跑通第一条任务（第 2、3 章）；
  3. 让它接上你自己的模型（第 4 章）；
  4. 学会在不同任务之间切换工作方式（第 5 章）；
  5. 能自己装插件、写插件、把插件交给别人（第 6、7 章）；
  6. 最后把它接到 Stata 上，做真正的计量工作（第 8—10 章）。

后三章是本书与通用教程最大的不同：不停留在“框架能干什么”，而是落在“计量研究者拿它干什么”。

本书的写法：三次消化#

写作时给自己定了三条规矩，也建议你按同样的层次去理解：

层次 做什么 对应本书内容
还原 把“是什么、怎么配”讲准，命令与字段不臆造 基础篇、插件篇

所以这本书不是“教程的复制粘贴”。同一个知识点，会尽量补三样东西：为什么是这样设计的、什么时候会踩坑、怎么判断自己真的做对了。

1.1 从“会说话”到“会做事”#

大模型本身只会做一件事：根据上下文预测下一段文字。它能告诉你“这段 Stata 代码应该用 reghdfe”，但它没法自己打开你的 .do 文件、跑一遍、看到 r(198) 之后再改。

把这件事补齐的中间层，就叫 Agent Harness（智能体框架）。

text
用户目标
   │
   ▼
┌─────────────┐     "该做什么、先做哪步"
│   Model     │ ──────────────────┐
└─────────────┘                   │
   ▲                              ▼
   │ 结果/报错/文件内容      ┌─────────────┐
   └────────────────────────│  Harness    │
                            │ 读文件 跑命令 │
                            │ 调工具 管会话 │
                            └─────────────┘

用一句更直白的话概括：

模型负责“想”，Harness 负责“做”。

同一个模型，配上不同的 Harness，能力边界完全不同。这也解释了一个常见困惑：为什么同样的模型，在网页版里只能聊天，在本地客户端里却能改你的代码、跑你的脚本——差别不在模型，在 Harness 给了它哪些工具、哪些权限。

1.2 DeepSeek Harness 是什么#

DeepSeek Harness 是深度求索开源的智能体框架，MIT 许可证，TypeScript 编写，命令行入口是 dsh。它的核心设计只有一句话：

Everything is a Plugin.（一切皆插件）

模型接入、工具、技能、会话管理、沙箱、存储、调度，甚至界面，全都是由插件拼出来的。内核（Cordis）只做三件事：加载插件、卸载插件、管理插件之间的依赖。

这带来一个很实际的好处：你不需要改源码，就能在配置层换掉自己不满意的那一部分。比如：

  • 不想用内置的文件编辑工具？换一个插件替代；
  • 公司要求所有请求走内部网关？加一个自定义模型提供方；
  • 想让 AI 能跑 Stata？挂一个 MCP 客户端插件，把 Stata 包装成工具。

把 Harness 想成一台可换零件的相机：机身（内核）负责快门和卡口，镜头（模型）、取景器（界面）、存储卡（会话日志）都能换。多数框架是“整机”，DeepSeek Harness 是“卡口标准”。

1.3 三个必须分清的概念#

初学者 90% 的困惑来自把这三个词混着用。先把它们摆清楚：

概念 回答的问题 举例
Profile（配置档） 这次启动，加载哪一整套应用配置？ web、headless、desktop、sdk
Agent 预设（模式） 这个会话里，模型能用哪些工具、按什么方式工作？ 标准模式、PTC 模式、极简模式、创作者模式
插件（Plugin） 具体某项能力由谁提供？ MCP 客户端、模型适配器、界面面板

三者的关系是嵌套的：

text
Profile（启动哪套配置）
   └── 插件组合（由 cordis.patch.yml 决定）
          └── Agent 预设（会话里选哪组工具）
                 └── 一次具体任务

这解释了一个高频故障：你用命令行给 web 这个 profile 装了插件，桌面版却看不到——因为桌面版用的是 desktop 这个 profile，两者互不相通（详见第 6、7 章）。

1.4 核心能力地图#

能力 具体表现 对使用者意味着什么
一切皆插件 Cordis 内核 + 配置层组合 能力可替换、可裁剪、可自己写
运行可追溯 模型看到的内容写入仅追加会话日志，Trajectory 视图可按来源查看 出问题能回放，复现过程可审计
四种运行模式 标准 / PTC / 极简 / 创作者 不同任务用不同“工作台”
多形态入口 桌面版、Web UI、headless、CLI、Python/TS SDK 手动用、脚本用、嵌入系统用都行
模型无关 DeepSeek 官方 + 目录提供方 + 自定义 OpenAI 兼容端点 不被单一厂商锁定
配置可导出 dsh --profile web --dump-config 环境可以存档、可以交给别人重建

其中“运行可追溯”最容易被低估。多数 Agent 工具只给你最终答案，DeepSeek Harness 会把模型每一步看到了什么、调了什么工具、拿到了什么返回都记下来。对做实证研究的人来说，这不是调试功能，而是研究记录——第 10 章会把它变成复现报告的一部分。

1.5 核心特性清单#

  • 一切皆插件：Cordis 内核只负责插件的加载、卸载与依赖管理；所有能力均由插件提供，配置层自由组合。
  • 运行有迹可循：模型看到的一切都写入仅追加设计的会话日志；Trajectory 视图按来源查看，恢复、分叉、检索与回放共享同一份事件流。
  • 多种运行模式：标准模式、PTC 模式、极简模式、创造模式。
  • 多形态使用：Web UI（默认 http://127.0.0.1:3080）、桌面版、headless、CLI、Python SDK、TypeScript SDK。
  • 工具与扩展丰富：文件编辑、Shell、检索、Skills、计划、目标、子代理、工作流；任何能力都可被 patch 替换。
  • 开放可控：MIT 开源；Profile + 组合包分层叠加配置，dsh --profile web --dump-config 可查看完整配置树。
  • 模型无关：填入 DeepSeek API 密钥即可用，支持其他提供方与自定义 OpenAI 兼容端点，模型路由无需重启。
  • 研究就绪：完整可观测的事件流与配置树，底层 Cordis 有学术论文支撑。

1.6 它适合谁，不适合谁#

适合：

人群 具体收益
开发者 本地 AI 编码助手，能力边界自己定，不被黑盒限制
研究者 全流程留痕，可回放、可归档、可写进方法附录
计量 / 统计用户 通过 MCP 接 Stata，把“跑回归”变成对话式操作
工具折腾爱好者 插件系统本身就是可玩的东西

不太适合（至少现在）：

  • 想零配置开箱即用的人：桌面版已经简单很多，但涉及 MCP、插件时仍要改 YAML；
  • 不能接受预览版波动的人：项目仍标注为预览阶段，破坏性更新是可能的，重要环境请固定版本；
  • 需要企业级权限审计的团队：个人版的能力边界清晰，但组织级管控要自己设计。

别把它当“更聪明的聊天框”。 它真正的价值在于“能动手”——而“能动手”同时意味着“能搞坏东西”。第 3 章的访问模式、第 10 章的只读原则，都是为此准备的。

1.7 与常见工具的差别（个人判断）#

以下是比较主观的观察，供你选型时参考：

维度 IDE 内置 Agent 命令行 Agent DeepSeek Harness
上手成本 最低 中 中偏高
可替换性 低（绑定 IDE） 中 高（连界面都能换）
可审计性 一般 一般 强（仅追加日志 + 配置树导出）
扩展方式 插件市场为主 自定义脚本 插件 + MCP + 配置补丁
适合场景 日常编码 自动化脚本 需要定制与留痕的长期工作流

一句话：如果你只需要“帮我改这段代码”，不必上 Harness；如果你想要一个“能被改造、能被审计、能被复现”的工作台，它值得花时间。

  3. Profile ≠ 模式 ≠ 插件：启动配置、会话工具集、单项能力，三个层次不要混。
  4. 可审计是它的差异化优势：仅追加日志 + 配置树导出，让“AI 做过什么”有据可查。

2.10 常见问题与排错#

问题 1：浏览器打不开 http://127.0.0.1:3080

问题 5：Python SDK 运行时找不到 Node.js

SDK 自带运行时，正常不需要系统 Node.js；确认安装的是完整包 python -m pip install deepseek-harness-sdk，并核对平台要求（Linux x64/arm64、macOS 14+ arm64、Windows x64）。

第 3 章 DeepSeek Harness 桌面版

工作区、访问模式与两次实战

📖 第 3 章 ⏱ 约 6 分钟 🔖 2,458 字

本章要解决的问题#

  • 桌面版和网页版的本质区别是什么？
  • “工作区”为什么是必选项，而不是可选项？
  • 第一次用它干活，怎么在不冒险的前提下摸清它的脾气？

3.1 桌面版到底是什么#

很多人以为桌面版只是“把网页包了个壳”。实际不是。

桌面版把三样东西打包在一起：

text
┌──────────────────────────────────────────┐
│  桌面应用                                 │
│  ┌────────────┐  ┌──────────┐  ┌────────┐│
│  │  Web 界面  │  │  dsh 运行时│  │ 托盘   ││
│  │ （会话/插件）│  │（工具/沙箱）│  │（常驻）││
│  └────────────┘  └──────────┘  └────────┘│
└──────────────────────────────────────────┘
  • 界面：会话、工作区、插件管理、设置；
  • 运行时：真正执行工具、读写文件、起子进程的那一层；
  • 托盘进程：让它在关掉窗口后仍能继续跑任务。

第三点很关键，也是后面无数“改了配置却不生效”的根源：关窗口不等于退出进程。Windows 要右键托盘图标退出，macOS 要 Cmd+Q。

3.2 界面四区，各管什么#

区域 你在这里做什么 容易忽略的点
左侧导航 新会话、工作区、插件、设置 插件入口在这里，不在设置里
中央会话区 看回答、看执行步骤、看工具结果 要展开工具调用看细节，别只看结论
底部输入区 写任务、@文件、选模型 工作区没选时，这里是灰的
右上角 展开侧边栏（浏览器、终端） 内置终端在排错时很好用

一个使用习惯

看会话不要只看最后一段话。真正有价值的信息在工具调用记录里：

text
▸ 读取文件  D:\demo\auto.csv          ← 读了哪个文件
  参数: { path: "auto.csv" }
  返回: 74 行 × 12 列                 ← 实际拿到了什么
▸ 执行命令  python analyze.py         ← 跑了什么
  退出码: 0

模型可能把“没读到文件”说成“数据是空的”。以上面的记录为准，不以模型的叙述为准——这条原则会贯穿全书。

3.3 首次配置：只做三件事#

第一件：填模型

路径：左下角账号菜单 → 设置 → 模型。

字段 填什么
模型提供方 先选 DeepSeek 官方
API Key 你的密钥，保存后界面只显示脱敏描述
模型 从当前可用列表里选

填完保存，不需要重启，下一次请求就生效。

第二件：加工作区

点侧栏“工作区”旁的加号，选一个目录。

加进去 ≠ 选中。 添加只是把目录登记到列表里，还要在输入框上方的“选择工作区”里明确选中它。这是“输入框灰着不能打字”最常见的原因。

第三件：选择工作区并创建会话

在系统选择器中选中目标文件夹（建议先用一个独立的测试目录，例如只含 README.md 和 auto.csv 的 demo 目录）。

回到新会话，在输入框上方的选择工作区中选中该目录。Agent 预设选择标准模式；在输入区底部选择已配置的模型。

访问模式与 Agent 预设相互独立，通常有：仅可查看、工作区内修改、完全权限 三档。

  • 首次统计任务选择“仅可查看”，确认写入需求后再切换为“工作区内修改”；
  • “工作区内修改”主要限制文件写入，不要把它理解成禁止读取所有工作区外路径或隔断网络；
  • 只读任务提示词不会自动收紧沙箱权限，权限以访问模式实际策略为准。

为什么工作区是强制的

因为 Harness 的所有文件操作都要有一个根：

  • 相对路径相对于它解析；
  • 访问模式（能否写、能否出界）以它为边界；
  • 会话日志记录的文件路径也以它为基准。

没有根，工具就不知道该往哪儿动手。这不是产品偷懒，而是安全模型的必要前提。

3.4 访问模式：三档权限，别当装饰#

档位 允许什么 什么时候用
仅可查看 只读，不写文件 第一次接触新项目、审计数据、读论文代码
工作区内修改 可写，但限制在工作区内 日常开发、跑分析脚本
完全权限 基本不限制 明确知道自己在做什么时，短时使用

三点必须说清楚：

  1. 提示词里写“只读”不会自动收紧权限。 权限由访问模式决定，提示词只是“请求”，不是“策略”。
  2. “工作区内修改”限制的是写入，不要理解成“禁止读取工作区外的一切”或“断网”。
  3. 第三档不是“高级功能”，是“高风险功能”。用完就调回来。

养成一个动作：每个新项目的第一条指令都用“仅可查看”，等确认它读对了目录、认对了文件，再升到“工作区内修改”。这个习惯能挡掉大部分事故。

3.5 实战一：只读盘点一个数据目录#

假设工作区 D:\demo\ 里有 README.md、auto.csv（Stata 自带 auto 数据导出）、notes.md。

第一条指令：

text
请只读取当前工作区的 README.md 和 auto.csv 的表头与前 5 行。
完成三件事：
1. 用三句话概括这个目录是做什么的；
2. 报告 auto.csv 的列名、行数；
3. 指出哪些列看起来是数值型、哪些是字符型。
不要修改或创建任何文件。

验收标准（不是“回答得像不像”，而是这三个可核对的事实）：

检查项 期望

行数 74 行（不含表头）
类型判断 make 为字符型，price、mpg、weight 为数值型

如果它说“文件不存在”，先看工具记录里的路径——大概率是工作区选错了，或者用了相对路径解析到了别处。

3.6 实战二：让它产出一个可预览的结果页#

只读跑通后，做一次写入练习。目标不要定成“做个网站”，定成“把刚才的分析变成一张能打开看的卡片”：

text
基于 auto.csv，创建一个 report.html：
- 标题：auto 数据快速概览
- 内容：样本量、price 与 mpg 的均值/中位数/标准差、一张按 foreign 分组的均价条形图
- 用原生 HTML/CSS/JS，不引用任何外部库和 CDN
- 只允许创建 report.html，不要改动 README.md、auto.csv、notes.md
- 完成后确认文件存在，并告诉我怎么在浏览器打开

完成后做三件核对：

  1. 文件管理器里确实多了 report.html，大小不为 0；
  2. 浏览器打开，数字与 CSV 实际计算一致（可以自己用 Stata 或 Python 算一遍对照）；
  3. README.md、auto.csv 的修改时间没变。

第 3 点最容易被忽略，也最能验证“它有没有越界”。

迭代的正确姿势

想改的时候，一次只提一个目标：

  • 自定义网关接不通时，怎么快速定位是协议、字段还是模型声明的问题？
  • 已经有火山方舟 Coding Plan，怎么接进来？

4.1 三条接入路线#

类型 是什么 需要准备 适合
DeepSeek 官方 官方端点，开箱可用 一个 API Key 绝大多数人起点
目录提供方 dsh 内置目录里已有的厂商（Anthropic、OpenAI 等） 对应厂商凭据 已订阅其它模型
自定义提供方 目录里没有的端点（公司网关、自建服务） Provider ID、baseURL、协议、凭据、模型 内网、代理、私有部署

入口：

  • 桌面版：左下角账号菜单 → 设置 → 模型
  • Web UI：终端打印的地址 → 设置 → 模型

改完即刻生效，不用重启。原因是模型路由在每次请求时解析，而不是启动时固化。

4.2 密钥去哪了：理解“只写”机制#

保存之后，你会发现界面上再也看不到完整密钥。这不是显示 bug，而是设计如此。

text
你输入明文密钥
      │
      ▼
┌──────────────────┐        ┌─────────────────────────────┐
│ 设置界面（只写） │───────▶│ $DSH_HOME/.credentials.yaml │
└──────────────────┘        └─────────────────────────────┘
      │                              │
      ▼                              ▼
界面只拿到"凭据描述符"        配置文件里只留引用 ID
（脱敏，不含明文）            （例如 apiKeyEnv: XXX）

三个推论，都是实操中会撞上的：

  1. 配置文件里看不到密钥是正常的，不要以为没保存成功；
  2. 环境变量与已存凭据同名时，已存储的凭据优先——你在终端里 export DEEPSEEK_API_KEY=... 却发现没生效，很可能就是这个原因；
  3. 换机器时，.credentials.yaml 不会跟着配置走，需要重新填。

.credentials.yaml 是明文存储（受文件权限保护）。共享目录、同步盘、代码仓库里都不该出现它。团队协作时，配置模板里只写 apiKeyEnv，让每个人用自己的环境变量。

4.3 模型列表从哪来#

默认端点下的模型列表跟随官方发布列表：

  • 首次使用时加载；
  • 使用期间大约每 10 分钟后台刷新一次；
  • 加载失败时回退到内置列表，不影响已配置的模型。

有两个细节值得知道：

  • 卡片上展示的是内置模型；新发布的模型可能只出现在对话框的模型选择器里；
  • 如果你把模型目录改成手动维护，就不再跟随发布列表；想恢复，选“恢复默认模型”。

对研究场景的建议：写论文期间把模型目录固定下来。否则某天默认模型悄悄升级，你的复现结果会多出一个无法解释的变量。

4.4 目录提供方：省事，但有前提#

选“添加提供方” → 选厂商 → 填密钥，端点、协议、模型列表都由目录提供，不用手写。

但有些厂商用原生认证，只填一个 API Key 字段是不够的：

厂商 还需要
Bedrock AWS 凭据 + 区域
Vertex ADC 项目
Azure api-version
Codex OAuth 授权

路由 id 有固定约定，写配置时要对得上：Anthropic → anthropic，OpenAI → openai，Kimi → moonshotai，智谱 GLM → zai。

4.5 自定义提供方：字段不多，坑不少#

路径：添加模型提供商 → 自定义模型 API。

字段 说明 必填
Provider ID 小写，永久标识 是
显示名称 界面上显示的名字，可随时改 否
基础 URL 端点的 baseURL 是
API 协议 openai-completions / openai-responses / anthropic-messages 三选一 是
凭据 按服务端要求；支持时可用环境变量 视端点
模型 至少一个 是

Provider ID 为什么“永久”

它被写进了三个地方：请求路由、已保存会话的模型记录、凭据引用。改 ID 等于让这三处同时失效，所以产品干脆不允许改。

要改名怎么办？ 新建一个提供方，把模型配好，再删掉旧的。已有会话仍指向旧 ID，会报 UNKNOWN_MODEL——这是预期行为，不是 bug。

一个提供方只能有一种协议

openai-completions 和 anthropic-messages 的请求体结构不同，不能混在一个提供方里。公司网关同时暴露两种协议时，建两个提供方。

模型发现

模型目录里点“获取可用模型”，会按当前 baseURL 和凭据去查。端点不支持 /models 时，手动填模型 ID 即可。

选定某个模型后，它成为新会话的默认模型；已经发过请求的会话保留自己日志里的模型，不受影响。这个设计对复现很友好：旧会话不会因为你现在换了模型而“变味”。

4.6 推理等级：不是越高越好#

支持档位的模型，可以在模型选择器里选 off / low / high 等。

场景 建议档位 理由
批量格式整理、文件重命名 off / low 不需要推理，省钱省时间
常规编码、数据分析 默认档 平衡
复杂重构、跨文件推理 high 值得多花的 token

直连 DeepSeek 官方路由不需要额外配置，模型自带档位；插件配置里的 llm-deepseek.reasoningEffort 可以改默认起始档。

走 OpenAI 兼容网关时的两个开关

情况 配置
网关后的模型默认开启思考，你想关掉 路由加 compat.thinkingFormat: deepseek：off 档发 thinking: {type: disabled}，其它档补 enabled
想彻底隐藏某模型的档位选择 reasoningEfforts: false；之后若强行选择会报 UNSUPPORTED_REASONING_EFFORT

另外两个常见兼容开关：

  • compat.supportsDeveloperRole: false：部分网关拒绝 role: "developer"；
  • compat.maxTokensField: max_tokens：默认发的是 max_completion_tokens，老网关不认。

配置层级规则：路由级的 compat 是默认值，模型级逐字段覆盖。空值键（例如只写一个 supportsDeveloperRole: 后面不填）会被拒绝，而不是当成“忽略”。

4.7 图片输入：先声明，后使用#

dsh 对多模态采取“先声明后使用”策略：

  • 手动录入的模型默认按纯文本对待；
  • 给未声明图片能力的模型附图片，发送前就会被拒绝，并点名是哪个模型。

配置步骤：

  1. 编辑提供方 → 打开自定义设置（新建时直接在模型目录里加模型）；
  2. 展开该模型的选项 → 输入类型勾选“图片”，保留文本；
  3. 保存后开新会话，附一张测试图验证。

需要写文件时，位置是：

text
$DSH_HOME/profiles/<profile>/cordis.patch.yml

Web 默认 web，桌面版用设置页的“打开配置文件”定位真实路径。不要再往旧的 settings.yaml 里写模型配置。

yaml
# 文件路径：$DSH_HOME/profiles/web/cordis.patch.yml
- id: llm-pi-ai
  config:
    providers:
      my-gateway:
        apiKeyEnv: GATEWAY_API_KEY
        api: openai-completions
        baseURL: https://gateway.example/v1
        models:
          - id: legacy-chat
          - id: vision-preview
            input: [text, image]

三个细节：

  • input 作用于单个模型；不写时先继承目录声明，再回退到路由的 defaultInput（默认只有 text）；
  • 要给一批未描述模型统一开视觉，可在路由上写 defaultInput: [text, image]；
  • 内置提供方的单模型覆盖写在 modelOverrides 下（以模型 ID 为键）；DeepSeek 直连路由用的是 inputModalities，两套字段不能互抄。

input 是你对端点的断言，不是检查。你声明了图片能力，但端点其实不支持，请求会在服务端被拒。声明错了，报错会出现在“运行期”而不是“配置期”。

4.10 实战：接入火山方舟 Coding Plan#

如果你已经在用火山方舟 Coding Plan，可以把额度直接用在 DeepSeek Harness 上。要点只有三个：选对协议、选对 Base URL、填对模型名。三者错一个，表现都是“认证失败”或“模型不存在”，很容易误判成密钥问题。

4.10.1 先看核心参数

参数 取值 说明

  • 已订阅 Coding Plan 套餐（未订阅则先到方舟活动页按需订阅）；

4.10.3 方式一：Ark CLI 一键配置（推荐）

Ark CLI 是火山方舟官方的命令行工具，本地完成认证后可以把 provider 信息直接写进常用 AI Agent 的配置里，省掉手填 baseURL、协议、模型名这三步最容易出错的操作。

安装、登录与写入的具体命令以方舟官网文档为准（各版本会变），你只需要记住三步的判断标准：

  1. 认证成功：CLI 能列出你的套餐与可用模型；
  2. 写入成功：DSH 的模型页里出现 ark 相关提供方，不是空列表；

先给结论，后面全部围绕它展开：

模式不是模型的档位，而是插件组合的预设。

text
Profile：决定启动哪套应用（web / desktop / headless）
   │
   └── 模式：决定这个会话加载哪组插件
          ├── 标准：文件 + Shell + 搜索 + 子代理 + 计划
          ├── PTC：上述能力 + 收拢为 run_code
          ├── 极简：只剩 bash + 文件编辑器
          └── 创作者：标准能力 + 运行时检查 + 热加载试验

所以切换模式不会让模型变聪明，只是换了一套工具和工作方式。选哪个，取决于你手里是什么活。

5.2 四种模式一览#

模式 一句话 典型场景 代价

5.3 标准模式：默认就选它#

如果你不知道选哪个，选标准模式。它提供：

能力 用起来是什么感觉
文件读写编辑 能看项目、能改代码
执行终端命令 跑脚本、跑测试，执行前有确认
联网搜索 查文档、查报错
子智能体 把子任务丢出去并行处理
计划模式 先给方案，你点头再动手

新手最容易犯的错是“上来就让它改生产代码”。正确顺序：只读任务 → 小范围写入 → 完整任务。每一步都用工具记录核对，而不是看它说“已完成”。

5.4 PTC 模式：把多轮调用压成一段程序#

PTC = Programmatic Tool Calling（程序化工具调用）。它背后的观察很朴素：

模型写代码，比一步一步吐工具调用更稳。

普通模式 vs PTC

对比 标准模式 PTC 模式
交互形态 调一个工具 → 看结果 → 再调下一个 写一段 TypeScript → 一次提交执行
上下文占用 每步中间结果都进对话 只有返回值和日志回到对话
适合 步骤少、目标明确 步骤多、逻辑固定、需要循环/判断

在 PTC 模式下，界面上只暴露一个 run_code 工具；其它工具以 SDK 形式出现在代码里，用 await tools.xxx() 调用。

typescript
// PTC 程序示意：一次提交，在会话沙箱的独立进程中执行
const files = await tools.list_files({ path: "do" });            // 只读，可与下一行并行
const dict  = await tools.read_file({ path: "docs/codebook.md" }); // 互不依赖

// 只把结论返回给模型，中间过程不占上下文
const doFiles = files.entries.filter(f => f.endsWith(".do"));
return {
  doCount: doFiles.length,
  doFiles,
  dictHead: dict.text.slice(0, 200),
};

执行语义

  • 运行在会话沙箱策略之下的独立托管进程里；
  • 子调用仍走统一工具流水线，审批与钩子照常生效——PTC 不是“绕过审批的后门”；
  • 独立的只读调用可以并行（默认上限 10 路）；会改状态的操作按提交顺序串行。

什么时候值得切

值得 不值得
要遍历 30 个 .do 文件做统一替换 只改一个文件的一行
批量读 100 个 CSV 的表头做汇总 读一个文件回答问题
固定流程的流水线（清洗→回归→导出） 探索性任务，下一步取决于上一步结果

5.5 极简模式：一把尺子，不是一台轮椅#

极简模式常年被误解。它只保留两个工具：

  • 持久化 bash；
  • str_replace_editor（文件编辑器）。

它不是为低配电脑准备的，而是为归因准备的：

你想知道 极简模式怎么帮你
这个任务是模型能力不够，还是工具太好用？ 把工具削到最少，看模型裸奔能跑多远
换模型后提升来自模型还是来自 Harness？ 固定环境，只换模型，结果可比
某个失败是环境问题还是理解问题？ 用极简环境复现，排除工具干扰

DeepSeek 自己的代码智能体基准就用极简模式跑。原因很直接：评测要公平，就不能让 Harness 帮太多忙。

所以日常干活别用它。它不是“轻量版标准模式”，是“对照组”。

5.6 创作者模式：把 Harness 当素材#

前三种模式的工作对象是你的任务；创作者模式的工作对象是 Harness 自己。

四项能力：

能力 干什么 实际价值
检查运行时 看当前加载了哪些插件、服务、依赖 动手前先知道能接在哪
内存中试验 新插件先加载到当前会话内存 不改源码、不重启，试错成本极低
自然语言生成插件 你描述，它查接口、写代码、加载 不会 TS 也能定制
固化为预设 把可用组合保存成新模式 造出你自己的“第五种模式”

从一条能用的提示词开始

好提示词包含四件事：位置 + 功能 + 外观 + 约束。

text
帮我加一个插件：
- 位置：右侧栏面板
- 功能：读取工作区 output/ 下最新的回归结果表（csv），
        显示系数、标准误、显著性星号，支持按变量名搜索

5.9 安全边界#

风险 说明 做法

本章速记#

  1. 模式 = 预设插件组合，不是模型档位。
  2. 标准是基座，PTC 和创作者做加法，极简做减法。
  3. PTC 省的是上下文，不是审批——审批照旧。
  4. 极简模式是评测对照组，不是低配版。
  5. 创作者模式改的是 Harness，产出是会运行的代码。

  • 同一个任务（例如“统计 do 目录下所有 .do 文件的行数”）分别用标准模式和 PTC 模式跑一次，比较工具调用次数与上下文长度；
  • 在创作者模式里做一个只读的小面板，然后用“检查运行时”看它依赖了哪些服务；
  • 把极简模式跑一次失败任务，记录它的报错，再用标准模式跑同一个任务，对比差异。

本章要解决的问题#

  • 一个插件从“文件存在”到“模型能用”，中间经过哪几步？
  • 为什么配置写得很像样，却完全没有生效、也没有报错？
  • 安装完怎么验证，而不是自我安慰“应该装上了”？

6.1 先分清两个层次#

这是本章最重要的一张表。混淆它，后面的问题会解释不清：

层次 名字 决定什么 在哪里改
应用层 profile 启动时加载哪一整套配置 $DSH_HOME/profiles/<profile>/
会话层 Agent 预设（模式） 这个会话里模型能用哪些工具 会话界面选择

一个插件装进了 web 这个 profile，只说明“用 web 启动时它会被加载”；你在桌面版（desktop profile）里当然看不到它。

同理：在 desktop profile 里装了插件，但会话选的是“极简模式”，工具被裁掉了，也不代表插件没装上。

6.2 插件长什么样#

桌面版左侧“插件”页能看到两类东西：官方与社区提供的成形插件，以及你自己开发的本地插件。

不管界面怎么展示，最小形态就是一个导出 apply 的 TypeScript 模块。框架加载时调用 apply(ctx)，你通过 ctx 注册能力（工具、事件监听、模型适配器等）。

typescript
// 文件路径：demo-plugin/src/index.ts
import type { Context } from '@deepseek-ai/cordis'

// 插件名：出现在日志与配置里，便于定位
export const name = 'demo-plugin'

// 入口：加载时被调用一次
export function apply(ctx: Context) {
  console.log('[demo-plugin] loaded')
}

三种写法，按需要选：

形态 写法 什么时候用
函数 导出独立 apply 大多数情况，最简单
对象 export default { name, inject, apply } 需要声明依赖等元信息
类 export default class extends Service 要向别的插件提供服务

不要画蛇添足加 export default。 Loader 优先取 default 导出；如果你用函数形态又加了一行 export default apply，命名空间上声明的 inject 会被整个丢掉，插件会在“零依赖”状态下启动——看起来加载成功，实际缺服务。

6.3 让插件接受配置#

硬编码的参数是维护灾难。把可调项抽出来，用 Schemastery 声明默认值：

typescript
// 文件路径：demo-plugin/src/index.ts
import type { Context } from '@deepseek-ai/cordis'
import Schema from '@deepseek-ai/schemastery'

export const name = 'demo-plugin'

export interface Config {
  greeting: string      // 问候语
  maxRetries: number    // 最大重试次数
  verbose?: boolean     // 是否输出详细日志
}

// 同名 Config：默认值在这里
export const Config: Schema<Config> = Schema.object({
  greeting: Schema.string().default('Hello'),
  maxRetries: Schema.number().default(3),
  verbose: Schema.boolean().default(false),
})

// 第二个参数是校验后的配置
export function apply(ctx: Context, config: Config) {
  console.log(config.greeting)
}

配置写在 profile 的补丁文件里：

yaml
# 文件路径：demo-plugin/cordis.yml（插件自带示例）
- insert:
    - id: demo
      name: '/absolute/path/to/demo-plugin/src/index.ts'   # 必须是绝对路径
      config:
        greeting: 'Hi'
        maxRetries: 5

判断一个参数该不该提成配置，只问一句：

能不能不改代码就改这个值？

不能，就提出来。另外，配置非法时插件应当明确报错并停止，不要带着半截配置继续跑——静默降级比崩溃更难查。

6.4 加载机制：insert: 是唯一的入口#

插件的加载与替换都发生在 profile 的补丁文件里：

text
$DSH_HOME/profiles/<profile>/cordis.patch.yml

核心语法：

yaml
- insert:
    - id: demo
      name: '/absolute/path/to/demo-plugin/src/index.ts'
      config: { }

insert: 到底做了什么

它表示“往配置树的这个位置插入一条插件条目”。

对比另一种写法：

yaml
- id: demo            # ❌ 裸条目
  config: { }

裸 - id: 的语义是“覆盖已存在的配置行”。如果配置树里根本没有 demo 这一行，它就是在覆盖一个不存在的东西——什么都不做，也不报错。

这就是“配置看着没问题、插件就是不见”的第一大原因。MCP 挂载（第 8、9 章）栽的也是这个坑。

三个必须记住的认知

# 认知 后果
1 裸 - id: 是覆盖，不是新增 目标不存在时静默无效
2 插件 Config 是判别联合，必填字段缺失会导致整份校验失败 少一个 transport 就整体不加载
3 可选组件加载失败常常静默跳过 界面无提示，模型说“没这个工具”

补丁会被程序改写

dsh 自己也会写这个文件（例如安装插件时重排条目）。所以：每次改动前先备份。

bash
# Windows PowerShell
Copy-Item "$env:USERPROFILE\.dsh\profiles\desktop\cordis.patch.yml" `
  "$env:USERPROFILE\.dsh\profiles\desktop\cordis.patch.yml.bak-$(Get-Date -Format yyyyMMdd-HHmmss)"

# macOS / Linux
cp ~/.dsh/profiles/desktop/cordis.patch.yml \
   ~/.dsh/profiles/desktop/cordis.patch.yml.bak-$(date +%Y%m%d-%H%M%S)

改完先校验 YAML 没写坏（缩进、中文冒号、Tab 都是常客）：

bash
python -c "import yaml,io;d=yaml.safe_load(io.open(r'<文件路径>',encoding='utf-8'));print('OK, 顶层条目', len(d))"

再确认条目真的进了配置树：

bash
dsh --profile web --dump-config

6.5 在应用里找插件#

桌面版左侧“插件”页：

  1. 先看已安装，确认现有的能力边界；
  2. 进发现页，检查索引源是否配置好、能否刷新；
  3. 打开详情，核对用途、版本、兼容范围、来源（npm 包还是 Git 仓库）；
  4. 点安装，读确认框里的实际来源再决定。

索引校验通过只代表“格式合法”，不代表官方审核过作者、代码或安全性。发现页没有合适的，就去 GitHub 按 dsh-plugin 话题找源码，自己看维护状态与依赖。

用创造模式做本地插件

  1. 在创作者模式里描述需求，等它写完；
  2. 复制它给出的插件绝对路径；
  3. 左侧插件 → 添加插件 → 填路径；
  4. 启用；
  5. 回到插件列表确认出现新条目与入口。

启用之后如果没反应，先按 6.7 的四项检查走一遍，不要急着重装。

6.6 用 CLI 装到指定 profile#

bash
# npm 上的精确版本
dsh plugin --profile web add your-plugin@1.2.3

# 本地开发的插件目录
dsh plugin --profile web add ./demo-plugin

# 看最终组合
dsh --profile web --dump-config

三个前提：

  • 包要声明 dsh.bundle 才能贡献配置层。普通依赖装成功 ≠ 能力已加载；
  • CLI 只影响指定 profile。给 web 装的不会自动出现在 desktop；
  • 装第三方包时用固定版本或确切 commit，别追默认分支。

6.7 安装后的四项验收#

检查 通过标志 不通过时查什么
兼容性 安装器接受当前 dsh 版本 engines.dsh、peer 依赖范围
配置加载 --dump-config 里有该条目 安装目标 profile、bundle 声明、patch 路径
依赖就绪 插件处于激活状态，不是“等待依赖” inject 声明的服务当前组合是否提供
实际能力 新会话里工具被真实调用 插件日志、工具返回

第四项是唯一的终审。判断方式很土但有效：

text
用 demo 插件跑一次，把返回值贴出来。

看到真实返回，才算通。不要问模型“你有哪些工具”——模型对自身工具表的自省并不可靠，答“没有”不代表没挂上，答“有”也可能是从上下文里猜的。

6.8 常见失败模式#

现象 最可能原因 快速验证
装完完全没变化 装到了别的 profile --dump-config 看目标 profile
配置树里没有条目 用了裸 - id: 改成 - insert: 列表
整份配置失效 缺必填字段（如 transport） 看启动日志的校验报错
插件“已安装”但工具不出现 依赖服务没提供 查 inject 与当前组合
改了配置没生效 进程没真正退出 结束托盘进程后重启
老会话里没有新工具 工具表是启动快照 开新会话

本章速记#

  1. profile 管启动、模式管会话，两个层次别混。
  2. insert: 是唯一入口；裸 - id: 只是覆盖，目标不存在就静默无效。
  3. Config 是判别联合，缺一个必填字段整份配置就不过。
  4. 装完先看 --dump-config，再用“真实调用一次”做终审。
  5. 补丁文件会被程序改写，改前先备份。

7.1 使用：三条规则#

规则一：新会话才看得见

插件提供的工具会进入新会话的工具表；提供的界面（侧栏、悬浮窗）会出现在应用对应位置。

但旧会话的工具表是启动时快照：

text
会话 A（启动时创建）── 工具表已固定
   │
   ├─ 期间安装插件 X
   │
   └─ 会话 A 仍然看不到 X 的工具
        要看到 → 开新会话，或彻底重启应用

所以“装完没反应”的第一步不是重装，而是开个新会话试试。

规则二：插件工具和内置工具同一条流水线

插件注册的工具不会绕过审批、钩子、沙箱策略。这对安全是好事，对调试是提示：插件调用失败，可能不是插件的问题，而是被沙箱策略拦了。

规则三：用 Trajectory 看真相

Trajectory 视图能看到每次工具调用的入参与返回。判断插件行为是否正常，看这里，不看模型总结。

7.2 改配置会热替换，改代码不会#

你改了什么 会发生什么
cordis.patch.yml 里某个插件的 config 框架卸载旧实例、加载新实例（HMR），不用重启
插件源码（.ts） 通常需要重载/重启，取决于是否启用监听
插件的依赖版本 需要重新安装并重启

热替换之所以干净，是因为插件注册的能力都挂在 effect 上，实例卸载时会自动清理，不会留下“幽灵注册”。

7.3 健康检查：四个问题#

问题 怎么查
加载了吗 dsh --profile <name> --dump-config 里有没有该条目
依赖齐吗 inject 声明的服务，当前组合是否提供
工具真被调用了吗 新会话说一句触发指令，看工具结果
行为对吗 会话日志、插件自身输出

别用“你有哪些工具”来判断。 模型无法可靠自省工具表。唯一可信的证据是：下一条指令 → 触发一次调用 → 看返回值。

一个可复用的验证话术：

text
用 demo 插件的 greet 工具，问候语用 "hi"，重试 2 次。
把工具的原始返回贴出来，不要改写。

要求它“贴原始返回”，能有效防止模型用自然语言掩盖失败。

7.4 发布：三种途径，差别在“装到的是什么”#

方式 用户命令 装到的东西 需要构建授权
npm dsh plugin add your-pkg 预构建的 lib/ 不需要
tarball dsh plugin add ./pkg-0.1.0.tgz pnpm pack 的产物 不需要
Git dsh plugin --profile demo add github:you/pkg 源码 需要（pnpm ≥ 10）

这张表的最后一列，是绝大多数“我这里好好的，用户装了就报错”的根源。

7.5 Git 安装：为什么 TypeScript 包会失败#

Git 安装拉的是源码。整个链路里没有任何一步会运行你的 build，所以 TypeScript 包到手时没有 lib/，加载自然失败。

text
作者仓库（src/*.ts）
      │  git clone / pnpm add github:...
      ▼
用户机器上的 node_modules/your-pkg/
      ├── src/        ← 有
      └── lib/        ← 没有（没人跑 build）
                 │
                 ▼
           加载入口不存在 → 失败

修法要两边各做一件事。

作者侧：提供自包含的 prepare

pnpm 在 git 安装后会执行 prepare。它必须自包含：

  • 不能假设“旁边还有一份 monorepo 源码”；
  • 不能依赖只在开发环境存在的路径映射；
  • 不要做类型检查（用户机器上未必有完整 devDependencies）。

实践做法：让 prepare 跑一份专用的打包配置，直接转译 src/：

json
{
  "name": "dsh-demo-plugin",
  "scripts": {
    "prepare": "tsdown -c tsdown.publish.ts"
  }
}

用户侧：为构建脚本授权

pnpm ≥ 10 默认拒绝执行 git 依赖的 prepare，所以第一次 add 会失败。这不是 bug，是供应链安全设计——构建脚本能在你的机器上执行任意代码，且不在 Agent 的沙箱里。

失败信息里会给出确切的包键。把它复制到该 profile 的 pnpm-workspace.yaml：

yaml
# 文件路径：$DSH_HOME/profiles/demo/pnpm-workspace.yaml
allowBuilds:
  dsh-demo-plugin: true

再执行一次 add 就通过了。

这项授权的实质是：允许该包在安装时于你的机器上运行代码，且不受 Agent 沙箱约束。只对源码可信、或你审过的包授权。不要图省事写 allowBuilds: { "*": true }。

锁定 commit

bash
dsh plugin --profile demo add github:you/demo-plugin#a1b2c3d

理由很实际：分支会动，commit 不会。锁定之后，作者后续推送无法悄悄改变你机器上实际运行的代码。

7.6 npm 与 tarball：让用户零授权#

不想让用户碰 allowBuilds，就把构建产物发出去。

npm 路线：

bash
# 作者侧：先构建，再发布
pnpm build
pnpm publish

# 用户侧：装的是 lib/，无需授权
dsh plugin add your-pkg

tarball 路线（内网/私有交付常用）：

bash
# 作者侧
pnpm pack            # 得到 your-pkg-0.1.0.tgz

# 用户侧
dsh plugin add ./your-pkg-0.1.0.tgz

两条路线都要求 package.json 的 files 字段包含 lib/，否则打出来的包里没有产物——这是“本地能用、发出去不能用”的第二个常见原因。

7.7 发布前的自检清单#

发布一次就会有人装，装坏了浪费的是别人的时间。按顺序过一遍：

# 检查项 通过标准
1 files 是否包含产物 npm pack --dry-run 能看到 lib/
2 main/exports 指向的文件存在 在干净目录装一次，require/import 不报错
3 是否声明 dsh.bundle --dump-config 里有条目
4 版本号语义 破坏性改动升 major
5 依赖范围 不要 *，不要依赖本地路径
6 权限最小化 不需要的能力不要申请
7 README 写清安装方式 用户知道该用哪条命令

7.8 版本与兼容策略（个人建议）#

场景 建议
内部自用 0.x 快速迭代，锁 commit 分发
小范围共享 每次发版写 changelog，注明最低 dsh 版本
公开包 语义化版本 + engines.dsh 明确下限
破坏性变更 升 major，并在 README 顶部提示迁移方式

dsh 本身在预览期，插件生态也在变。把兼容范围写进 engines，比在 README 里写“应该能用”负责得多。

7.9 安全边界#

风险点 说明 做法
构建脚本 安装时执行，不在沙箱内 只对可信包开 allowBuilds
插件运行权限 与内置工具同级，能读写工作区 审代码，尤其是文件与网络操作
供应链 依赖树里任何一个包都可能带脚本 锁版本、看 lockfile 变更
密钥 插件可能读到环境变量 不要把密钥放在全局环境变量里

本章速记#

  1. 装完看不到工具，先开新会话，再怀疑安装。
  2. 改 config 是热替换，改代码要重载。
  3. Git 装源码，npm/tarball 装产物——这决定用户要不要授权。
  4. prepare 必须自包含，别假设 monorepo 存在。
  5. 锁 commit，是防止“代码悄悄变了”的最低成本手段。

延伸练习#

  • 把同一个插件分别用 tarball 和 Git 两种方式安装，记录用户侧的操作差异；
  • 在干净目录里 npm pack 后解压，检查 lib/ 是否真的在包里；
  • 写一份 200 字的插件 README，只讲“怎么装、装完怎么验证”，逼自己把关键信息说清楚。

轻量执行通道的三条硬性要求

📖 第 8 章 ⏱ 约 6 分钟 🔖 2,456 字

本章要解决的问题#

  • 轻量执行通道和结构化结果通道，怎么选？
  • 一段 MCP 挂载配置，为什么少一行就完全无效？
  • Stata 许可只有一个，两个通道同时开会发生什么？

8.1 它是什么：一根“能跑就行”的管子#

Stata-Kernel-Jupyter（下称 SKJ）源自 Jupyter 生态里的 Stata 内核，MCP 化之后对外只暴露三个工具：

工具 作用 返回什么
stata_run 执行一段 Stata 代码 原始文本结果（含日志）
stata_help 查离线帮助 帮助文本
stata_dataset 看当前数据集结构 变量、观测等描述信息

它的设计目标很朴素：把代码交给 Stata，把结果原样带回来。

这既是优点也是局限：

  • 优点：轻、直接、启动快、行为可预测；
  • 局限：结果是非结构化文本，要靠模型自己从日志里找数字。

对比 AIStata MCP 的 23 个工具（第 9 章），差别不是“强弱”，而是“要不要结构化”。

8.2 两条通道怎么选#

维度 SKJ AIStata MCP
工具数量 3 23
结果形态 纯文本执行结果 结构化 RunResult（ok/log/returns/dataset）
数据审计 需自己写代码 内置 data_audit / codebook
图形 需自己导出 get_graph 直接取
长任务 无 stata_run_async + stata_job_status
适合 快速验证语法、查帮助、教学演示 复现工程、结果抓取、数据体检
建议 二选一 主力通道

决策很简单：

text
你要做的是一次性验证（这段代码语法对不对）？
   ├── 是 → SKJ 够用
   └── 否 → 你要拿回结构化结果（系数、R²、N）做后续处理？
             ├── 是 → AIStata
             └── 否 → 看许可：只能跑一个，就选 AIStata

Stata 许可会被抢占。 每条 MCP 通道都会拉一个独立的 Stata 进程，各占一个席位。单机单许可时，两个客户端同时跑，必有一个报 unable to obtain a license。建议只保留一条通道；确需并存，也不要同时执行任务。

8.3 接入：写在 profile 补丁里#

先说最容易走错的一步：

桌面版不读 ~/.deepseek/mcp.json。

往那儿写多少条都不会生效，模型永远说“我没有 stata 工具”。MCP 服务器必须挂在 profile 的 cordis.patch.yml 里。

文件位置：

平台 路径
Windows %USERPROFILE%\.dsh\profiles\desktop\cordis.patch.yml
macOS ~/.dsh/profiles/desktop/cordis.patch.yml

写法：

yaml
# 文件路径：上面那个 cordis.patch.yml
- insert:                                 # [1] 必须是 insert 列表
    - id: skj-mcp                         # 唯一 id，可自取
      name: "@deepseek-ai/dsh-mcp-client"
      config:
        serverName: stata-kernel-jupyter   # 工具前缀：mcp__stata-kernel-jupyter__*
        transport: stdio                  # [2] 必填，缺了静默失败
        command: 'C:\Python312\python.exe'        # Python 绝对路径
        args:
          - 'C:\skj\stata-kernel-jupyter-launcher.py'   # 启动器绝对路径
          - mcp
        env:
          PYTHONUTF8: '1'
          PYTHONIOENCODING: utf-8
        toolCallTimeoutMs: 600000         # 10 分钟，跑大 do 文件够用
        failOnStartupError: false

8.4 三条硬性要求#

缺一条就会“看起来配了、其实没挂上”：

# 要求 缺了会怎样
1 必须有 insert: 裸 - id: 只是覆盖一个不存在的行，等于没写
2 config.transport: stdio 判别联合缺必填字段，整份配置校验失败
3 改完彻底退出应用（含托盘） 旧会话工具表是启动快照，新开会话也不热加载

第 3 条最容易被“我重启了啊”糊弄过去：

  • Windows：关窗口只是最小化到托盘，要右键托盘图标 → 退出；
  • macOS：点红叉不退出，要 Cmd+Q。

验证是否真退干净：

bash
# Windows
tasklist | findstr -i deepseek

# macOS
pgrep -i deepseek
⚠️两个 schema 陷阱：
  1. idleTimeoutMs 不在 schema 里，写了会被静默剥掉，别浪费时间；
  2. 两个服务器的 serverName 不能重名，否则工具名冲突会被拒。

8.5 操作步骤#

text
1. 备份 cordis.patch.yml
2. 把挂载块追加到文件末尾（顶格，"- insert:" 不要缩进）
3. 校验 YAML：
   python -c "import yaml,io;d=yaml.safe_load(io.open(r'<路径>',encoding='utf-8'));print('OK')"
4. 彻底退出 DSH（含托盘），确认无残留进程
5. 重启，开新会话
6. 验证：让它执行 "display 2+3"，看返回是不是 5

第 6 步是唯一的验收标准。不要用“插件列表里有了”来判断——列表里有、工具没挂上，是很常见的状态。

8.6 三个使用场景#

场景一：对话式快速执行

把 DSH 当“会解释的 Stata 控制台”：

text
用 stata-kernel-jupyter 依次执行下面三行，并解释每一步的输出：
sysuse auto, clear
summarize price mpg
regress price mpg weight

期望结果可以核对：

项目 期望
观测数 74
price 均值 约 6165.26
回归 三个系数 + 标准误 + R²

如果数字对不上，先怀疑数据没加载成功（看日志里有没有 sysuse 的报错），再怀疑通道。

场景二：先查帮助，再写代码

stata_help 的价值在于“离线、原文”：

text
先查 xtreg 的语法和 vce(robust) 选项，再写一个固定效应模型示例，
并说明什么时候该用 fe 而不是 re。

比让模型凭记忆背语法可靠得多，尤其是老命令和历史版本差异。

场景三：教学演示

SKJ 本来就来自 Jupyter 内核，同一套执行层可以在 Notebook 里以 %%stata 单元格使用。教学时可以“Notebook 讲义 + DSH 问答”共用一条通道，学生看到的是同一套环境。

8.7 验证与排错#

验证（唯一可信的方法）：

text
用 stata-kernel-jupyter 跑 display 2+3

返回 5，说明三层全通：MCP 进程起得来 → Stata 能执行 → 结果能回传。

现象 最可能原因 怎么确认
模型说“没有 stata 工具” 没重启 / 缺 insert: / 缺 transport 逐项查 yml；确认进程真退出了
启动后行为异常、插件变少 yml 写坏了，回退到默认 yaml.safe_load 校验；回滚 .bak-*
工具名冲突 两个 server 用了同一个 serverName 改名
连上但一调就超时 默认超时太短 加 toolCallTimeoutMs: 600000
首次调用慢 5–20 秒 子进程空闲约 30 分钟自动退出 正常；下次调用重新拉起
中文变 ???? 缺 UTF-8 环境变量 补 PYTHONUTF8 / PYTHONIOENCODING

一个判断顺序

text
模型说没工具
   │
   ├─ yml 里有 insert: 吗？ ── 没有 → 加上
   ├─ config 里有 transport: stdio 吗？ ── 没有 → 加上
   ├─ 进程真退出了吗？ ── 没有 → 杀托盘进程重启
   └─ 都对了 → 命令行直接跑启动器，看它自己能不能起来

最后一步是分界线：启动器能跑 = 服务没问题，问题在客户端配置；启动器也起不来 = 环境问题，去查 Python 路径和包。

8.8 换机迁移#

项目 要做什么
cordis.patch.yml 用模板重写，旧文件里的 Python 路径全部作废
启动器路径 重新确认，不要照抄旧机器的盘符
旧的 ~/.deepseek/mcp.json 可以忽略（DSH 不读）；想干净就删
DSH 本体 新机器重装，装完才有 profiles/desktop/ 目录
Stata 确认许可有效，python -c "import pystata" 能过

本章速记#

  1. SKJ 是轻量执行通道：三个工具，纯文本结果。
  2. 挂载只在 cordis.patch.yml，mcp.json 是无效路径。
  3. insert: + transport: stdio + 彻底重启，三条缺一不可。
  4. 一个 Stata 许可只能一个实例，两条通道别同时跑。
  5. 验收标准是 display 2+3 返回 5，不是“配置看起来对”。

延伸练习#

9.1 它是什么：一层 Stata AI 接入层#

AIStata 的结构可以用一句话概括：

一个 Python 内核，多个前端。

VS Code 扩展、MCP 服务、CLI、Jupyter kernel、Python API 共用同一个 aistata 包，但不共享进程与会话。

这一点很重要：MCP 服务是独立进程，它有自己的 Stata 会话、自己的内存数据集。你在 VS Code 里 use 的数据，MCP 这边看不到，除非它自己也 use 一次。

本章只讲 MCP 这一面：23 个工具，以及它怎么接进 DeepSeek Harness。

9.2 一次调用的完整路径#

text
[1] DSH 读取 cordis.patch.yml
        │  spawn
        ▼
[2] python.exe ...\aistata-mcp-launcher.py mcp
        │  启动器：设 sys.path、设 UTF-8、转交 aistata.cli.main(['mcp'])
        ▼
[3] 握手：initialize / tools/list
        │  DSH 拿到 23 个工具的描述
        ▼
[4] 模型决定调用 stata_run
        │  DSH 通过 stdin 写一行 JSON-RPC
        ▼
[5] mcp.py 解析 → engine.py 选驱动（pystata 优先）→ 交给 Stata 执行
        │
        ▼
[6] 结果封装为 RunResult v1（ok / log / returns / dataset）
        │  stdout 回一行 JSON
        ▼
[7] 模型读到结构化结果，开始解释

为什么用 stdio 而不是 HTTP

维度 stdio HTTP
端口 不占 要分配、要防冲突
隔离 进程级天然隔离 靠服务端实现
兼容性 所有 MCP 客户端都支持 需要额外配置
排错 看进程是否起来 要看网络、端口、鉴权

实务结论：别去找端口号，也不用开防火墙。连不上就是进程起不来，去查 Python 路径、包路径和环境变量。

记住分组比记住名字有用——你需要的是“这类事该找谁”。

执行（5）

工具 用途 备注
stata_run 跑一段代码 多行用 \n
stata_run_file 跑 .do 文件 复现主力

9.4 挂载配置#

文件仍是那个：

text
%USERPROFILE%\.dsh\profiles\desktop\cordis.patch.yml     (Windows)
~/.dsh/profiles/desktop/cordis.patch.yml                 (macOS)
yaml
- insert:                              # [1] 必须是 insert 列表
    - id: aistata-mcp                  # 唯一 id
      name: "@deepseek-ai/dsh-mcp-client"
      config:
        serverName: aistata            # 工具前缀：mcp__aistata__*
        transport: stdio               # [2] 必填
        command: '<PYTHON>'            # python 绝对路径
        args:
          - '<LAUNCHER>'               # aistata-mcp-launcher.py 绝对路径
          - mcp
        env:
          PYTHONUTF8: '1'
          PYTHONIOENCODING: utf-8
        toolCallTimeoutMs: 600000      # 10 分钟
        failOnStartupError: false

四个要点：

  1. insert: 是列表，一次可以挂多个服务器（第 8、9 章两条通道可以写在同一份文件里）；
  2. toolCallTimeoutMs 在 schema 里；idleTimeoutMs 不在，写了会被剥掉；
  3. 两个 serverName 不能重名；
  4. 用便携启动器，不要直接 -m aistata。启动器自己会找包、设 UTF-8、做用户目录兜底，不依赖客户端传来的环境。

操作步骤

text
1. 备份 cordis.patch.yml
2. 追加挂载块（顶格）
3. 校验 YAML
4. 彻底退出 DSH（含托盘）
   Windows: tasklist | findstr -i deepseek
   macOS:   pgrep -i deepseek
5. 重启，开新会话
6. 验证：doctor + sysuse auto

验证指令：

text

9.5 “配了却没生效”：四个错误假设#

这是本章最值得读的部分。四层错误叠在一起，会形成一种很难受的状态：配置看起来全对、模型说没工具、也没有任何报错。

你以为 实际
扩展会把配置写进 ~/.deepseek/mcp.json，DSH 会读 DSH 桌面版完全不读这个文件，挂载点只有 profile 补丁
在 cordis.patch.yml 加一行 - id: aistata-mcp 就行 插入行里没有 mcp-client 这个 id，裸条目只是覆盖不存在的行
有 id 和 name 就够了 还缺 config.transport: stdio，整份配置校验失败
配置错了应该有报错 app-boot 对“可选 MCP 配置失败”不中止，于是静默不挂载
改完开个新会话就行 工具表是启动快照，必须彻底退出进程

理解这四条之后，再看第 8、9 章的配置，就会明白为什么我把 insert: 和 transport 标了序号——它们不是风格问题，是生死问题。

现象 / 报错 最可能原因 修法

第 10 章 论文复现专题

六阶段工作流与可审计报告

📖 第 10 章 ⏱ 约 5 分钟 🔖 2,196 字

本章要解决的问题#

  • 为什么“AI 帮我跑一遍”和“可复现”是两件事？
  • 六个阶段各自要交付什么，怎么验收？
  • 结果对不上时，按什么顺序排查？

10.1 复现的敌人不是代码，是“说不清”#

论文复现失败，多数时候不是作者写错了代码，而是：

  • 数据版本不明（同一份 .dta，不同年份下载内容不同）；
  • 包版本不同（reghdfe 新旧默认行为有差异）；
  • 样本筛选藏在某个 if 里，没写进正文；
  • 结果来自多次尝试中的一次，过程没留痕。

传统做法靠“人肉考古”。DeepSeek Harness 的价值在于：它把过程本身记录下来了。

dsh 特性 对复现的意义
仅追加会话日志 + Trajectory 模型看到的提示词、每次工具调用全部留痕，过程可审计
profile + --dump-config 环境配置可导出存档，别人能重建你的 Agent
headless 模式 阶段任务可脚本化，适合批处理与 CI
工具流水线（审批/沙箱） 高危操作（删数据、装包）默认要人批，防止污染原始数据
AIStata 23 工具 结构化结果、数据审计、图形抓取，信息量远大于裸跑 do

最后一条尤其关键：“AI 说跑出来了”不是证据，“get_table 返回的系数”才是证据。

前提：已按第 9 章挂好 AIStata MCP，并且

text
python <LAUNCHER> run "display 2+3" --json

返回 {"ok": true}。这一步不过，后面全是空谈。

10.2 六阶段工作流#

text
[1] 材料入库（论文 + 数据 + 代码）
        │
        ▼
[2] 建复现工作区，dsh 选中该目录
        │
        ▼
[3] 环境自检：doctor / check_dependencies
        │
        ▼
[4] 数据审计：describe_data / codebook / data_audit
        │
        ▼
[5] 跑主分析：stata_run_file / stata_run_async
        │
        ▼
[6] 结果核验：get_table / get_log / read_stata_log
        │
        ├── 不一致 → 诊断（reset_session 后分步重跑）→ 回到 [5]
        │
        └── 一致 → 图表 + 复现报告 + Trajectory 存档

六个阶段的顺序不是随便排的。环境在数据之前，数据在跑之前，核验在结论之前——每一步都在为下一步排除变量。

10.3 阶段一：材料入库与只读盘点#

把论文、README、数据、do 文件放进一个独立目录，例如：

text
D:\replication\
├── paper\           论文 PDF、附录
├── data\            原始数据（只读）
├── do\              作者代码
├── output\          你的产出（图表、表格、日志）
└── replication-checklist.md

在 dsh 里选中 D:\replication，第一条指令永远只读：

text
请只读取当前目录下的 README 和 do/ 目录中的 .do 文件名，回答：
1. 主表（Table 1/2）分别由哪个 do 文件生成；
2. data/ 下有哪些数据文件，各自大小；
3. 代码依赖哪些外部 Stata 包（如 reghdfe、ivreg2、estout）；
4. 哪些步骤看起来会写入或覆盖文件。
本轮只读取，不执行任何 Stata 命令，不修改任何文件。

验收标准：它的回答里出现的文件名，与你在资源管理器里看到的一致。不一致，说明工作区选错了。

开工前先备份数据。 把 data/ 整个复制一份到 data_backup/。访问模式优先用“工作区内修改”，“完全权限”留给确实需要的短时操作。

10.4 阶段二：环境自检#

text
用 aistata 的 doctor 做环境自检，然后用 check_dependencies
检查 reghdfe、ftools、estout、ivreg2 是否已安装。
缺什么列出来先告诉我，不要自动安装。

三个要点：

要点 原因
doctor 先跑 版本、版别、驱动（pystata 优先）、依赖状态一次看清
install_package 默认关 让 AI 先报告、人再决定，避免悄悄改环境
注意版本差异 论文可能是 Stata 14/15 时代代码，语法与默认行为不同

验收标准：拿到一张“已装/缺失”清单，且缺失项是你决定要不要补的，不是它自己补的。

10.5 阶段三：数据审计（跑代码之前）#

复现失败最常见的原因是数据对不上，不是代码写错。所以先审计：

text
依次执行，每步把结构化结果返回给我：
1. use "data/main.dta", clear
2. describe_data：观测数、变量数、类型
3. data_audit：重复 ID、缺失模式、明显异常值
4. codebook：因变量与核心解释变量的取值、标签、缺失
5. 把论文表 1 的描述性统计与数据实际值逐项对照，列出不一致项。

为什么强调“结构化结果”：describe_data 返回的观测数、变量类型是字段，不是一段话。字段可以核对，话不可以。

验收标准：样本量与论文表 1 一致；均值/标准差在合理误差内；不一致项被明确列出，而不是被一句“基本一致”带过。

10.6 阶段四：跑主分析#

text
用 stata_run_file 执行 do/table2.do。
执行前先告诉我这个文件会创建或覆盖哪些文件；
执行后用 get_table 把主回归的系数、标准误、R²、N 取出来，对照论文表 2。

工程要点：

情况 做法
大任务（bootstrap、模拟） stata_run_async + stata_job_status
输出被截断 get_log 取完整日志（截断策略通常是头尾截取 + 字符上限）
论文自带历史日志 read_stata_log 读 .log/.smcl 对照
跑完 close_session 释放许可席位

验收标准：get_table 返回的表里，系数、标准误、N 是具体数字，不是“约等于”。

10.7 阶段五：核验与差异诊断#

核验的黄金标准是逐表逐列对照，而不是“看起来差不多”。

让 dsh 维护一张清单：

text
创建 replication-checklist.md，逐行记录：
表号 | 列 | 变量 | 复现值 | 论文值 | 相对差异 | 状态（一致/不一致/待查）
先填 Table 2 的三列主结果。数值用 get_table 取，不要凭记忆抄。

对不上时，按这个顺序查

text
[1] reset_session 清内存 → 从 use 开始分步重跑
       （排除上一次运行残留的数据/宏污染）
[2] 核对样本筛选：if 条件、keep、权重，逐段看观测数
[3] 核对包版本：reghdfe / ivreg2 新旧默认选项差异
[4] 用 SKJ 通道做最小复现：裸执行，排除结果封装层的干扰
[5] 仍不一致 → 联系作者，附上你的环境与清单

第 ① 步能解决相当一部分“玄学差异”——上一轮跑过的 global、scalar、内存数据，都会影响下一轮。

验收标准：清单里每一行都有“一致/不一致/待查”的明确状态，没有空白。

10.10 六条守则#

守则 原因
原始数据只读，备份先行 AI 误操作不可逆，审批是兜底不是保险箱
install_package 默认关 防止悄悄改环境，先报告再人工放行
密钥不进复现包 复现包可能被共享或公开发表
每阶段一个会话 会话干净，Trajectory 清晰，问题好定位
Stata 单许可不并发 多客户端同时跑，必有一个报许可错误
结论必须核对原始输出 get_log/get_table 取回结果再下结论，不信转述

本章速记#

  1. 复现的核心不是“跑通”，是说得清。
  2. 六阶段：入库 → 环境 → 审计 → 执行 → 核验 → 报告，顺序不能乱。
  3. 审计在跑代码之前，因为数据错比代码错更常见。
  4. 差异诊断从 reset_session 开始，排除会话污染。
  5. 报告 + Trajectory + 配置导出，三件套才叫“可复现”。

延伸练习#

  • 拿一篇有公开数据的论文，只做阶段一至三，练习“只读盘点 + 环境 + 审计”；
  • 故意改一个样本筛选条件，看清单里的差异如何体现，练习写“差异诊断”；
  • 把复现报告模板填一遍，重点写“未复现项与原因假设”——这一节最能体现你的判断力。
